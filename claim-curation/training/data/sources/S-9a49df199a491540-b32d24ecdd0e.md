# Qwen3.6-35B block prefill on the NPU: how it caught the closed engine, what spinning OpenMP workers cost, open vs closed back to back

Sources (C:/code/openflowlm-next): `specs/open-engine/spec.md:3127-3130, 3213-3243, 3293-3298, 3314-3423, 3433-3488, 3609-3620, 3856`; `.claude/plans/archive/prefill-parity.md:90-111, 173-232, 250-257, 331-334`, `archive/prefill-parity-2026-09-21.md:24-78, 194-196, 219-222, 264-349`, `archive/gemm-context-collapse.md:60-71, 133-136`, `archive/oflm-omp-wait-policy.md:7-19, 57-67`; `pr-drafts/issue-vcomp-server.md:7-41`. Already curated: F-0100, F-0103, and the 662-2582-token performance/turbo/closed table (raw/fastflowlm/2026-09-22-oflm-hardware-hangs-timing.md).

## Route history (T = 256 tokens per block)

- First block route, 2026-09-11: GEMM dispatches 0.8 ms (512x2048) to 14 ms (12288x2048), rel_fro 2.2e-3. A 1020-token prompt went 121.4 -> 41.5 s (119 -> 41 ms/token). Per block: GEMMs 0.77-0.84 s (8%), host stages 1.5-2.0 s (17%), per-token MoE dispatches 7.1-7.9 s (73%) (spec.md:3213).
- Attention products moved to the NPU (40 dispatches, ~40 ms a block, replacing ~2.5 s of host attention at 2582 tokens): 2582 tokens 66.0 -> 54.6 s; the host stage stays flat at 1.23-1.37 s per block where host attention had grown it to 3.81 s (spec.md:3856, 2026-09-12).
- Host fixes 2026-09-13: the DeltaNet per-token half was 856 ms of a 1040 ms host stage; spreading it over tokens with OpenMP made it 165 ms. Value-initialised GEMM outputs wrote 716 MB of zeros per block. 2582 tokens 57.7 -> 41.6 s (spec.md:3215-3243).
- Kernel time alone (`--bench 8`, minima, 13-22% background CPU, 2026-09-13): gemm_n1024_k2048 0.82 ms; gemm_n2048_k4096 2.93; gemm_n2048_k512 0.56; ag_s4096 1.76; ag_pv4096 1.69; mb_s8 0.57; mb_s32 1.87; mb_s128 7.14; mb_s256 14.06; mx_linear 0.49 (gemm-context-collapse.md:60-71).
- With PASSIVE in force (2026-09-21), a 2582-token prefill is 19.46 s: 11.46 s of dispatch and 8.0 s of CPU (3.13 s DeltaNet), with no overlap. Dispatch logging itself costs ~1.2 s (spec.md:3393-3423).
- Full-attention layers leave and re-enter the GEMM context 110 times each way per prompt; a switch into `ag` costs +2.55 ms against +0.03 ms staying in `gemm`, ~0.66 s (3.4%) in all (spec.md:3402-3417).
- T is compiled in: a variant taking T from the RTP buffer built 2048 B smaller and deadlocked (gemm-context-collapse.md:133-136). At 2582 tokens the 22-token tail block cost 1760 ms, 62% of a full block (prefill-parity.md:331-334).
- The route turns on at 64 prompt tokens (`OFLM_OPEN_GEMM_BLOCK_MIN`) and is never used for a prompt with an image (spec.md:3127-3130).
- Host AVX2 DeltaNet conv (2026-10-07): 1024 tokens 9042 -> 8607 ms end to end. At 2582 tokens the gain could not be resolved: the NPU columns moved by up to 2.5 s between repetitions in one process, against a 0.35 s saving (spec.md:3362-3385).

## Spinning OpenMP workers slow the NPU

- 1122 tokens, one block, ms per dispatch, default (spinning) / PASSIVE / `OMP_NUM_THREADS=1` / kernel alone: gemm_n12288 17.59 / 11.61 / 11.58 / 9.47; gemm_n9216 14.13 / 9.58 / 9.32 / 6.78; mb_s256 26.39 / 16.99 / 16.95 / 14.57. Even 4 spinning threads throttle the dispatches fully (prefill-parity.md:173-232).
- 12 register-spinning processes with no memory traffic during `--bench-decode`: lm_head 11.54 -> 35.40 ms (43.7 -> 14.2 GB/s); step 120.5 -> 263.8 ms. The source infers the shared package power budget (prefill-parity.md:194-210).
- Trap: VCOMP140.DLL reads `OMP_WAIT_POLICY` (and `OMP_NUM_THREADS`) when it loads, before any static initialiser of the exe runs; `omp_get_max_threads()` stayed 24 when the exe set 10. `/DELAYLOAD:VCOMP140.DLL` fixes the CLI: 16.8 against 21.1 s at 2582 tokens (spec.md:3293-3298).
- In `oflm serve` eight closed model DLLs (`qwen3_6_moe_npu`, `qwen3_5vl_npu`, `qwen3_5_omni_npu`, `qwen3vl_npu`, `gemma_npu`, `gemma4e_npu`, `gemma4_12b_npu`, `gpt_oss_npu`) import vcomp, so vcomp loaded first. Server prefill PASSIVE against default: 1.74 / 2.33 s (182 tokens), 7.84 / 10.47 (1122), 17.43 / 24.14 (2593), 1.34-1.39x everywhere (prefill-parity-2026-09-21.md:264-294).
- Fix (#176, 2026-10-07): delay-load those eight DLLs too. The 35B q4_1 set then prefilled 135.5 / 137.3 tok/s at 1k and 138.7 / 140.3 at 2k, at parity with the variable set before launch. The q8 35B had prefilled 84-94 tok/s before the fix (109-118 with the variable). A missing DLL now fails at first use with 0xC06D007E instead of 0xC0000135 before `main()` (oflm-omp-wait-policy.md:17-19, 57-63).
- With PASSIVE the thread count reverses: 17.6 s at the full 24 threads against 19.5 s at 10; with spinning workers 20.4 against 18.9 s (prefill-parity-2026-09-21.md:67-78).

## Open against closed

- The closed engine prefills the whole prompt in one weight pass (log: "Prefill chunk 1/1 with 1122 tokens"; `--prefill-chunk-len` clamps to 512). 2593 tokens: closed 136.2 tok/s (19.0 s), closed chunked 59.0 tok/s (43.9 s), open with PASSIVE 86.3 tok/s (29.9 s) (prefill-parity.md:90-111, 2026-09-20).
- Back to back on 2026-09-21, same container: prefill open / closed 1.94 / 14.19 s (182 tokens), 8.95 / 18.85 (1122), 20.96 / 24.15 (2593); decode 8.38 / 14.17, 7.87 / 14.83, 7.00 / 14.46 tok/s (spec.md:3467-3477).
- Server with PASSIVE: open 20.76 and 25.96 s at 3062 and 3642 tokens against closed 20.94 and 23.05 s; fits server 0.46 s + N/153 tok/s, CLI 0.6 + N/164, default wait policy 0.39 + N/109. Context capacity 32768 against 4096 cost nothing measurable (prefill-parity-2026-09-21.md:264-294).

## Doubtful

- The closed engine's fixed prefill term moved between 9.93, 10.0, 12.1 and 14.8 s across fits (marginal rate stable at ~264-280 tok/s); its run-to-run spread at one length was 48-158 tok/s, so the open/closed crossover reads ~1700, ~3100, ~3600-3700 or "past 4800" tokens depending on the run.
- Closed decode on this box read ~6.8 tok/s in early September and 14.2-14.8 tok/s on 2026-09-21; the source notes the box's decode rate doubled without saying why. Bears on Q-0011.
- Open prefill went 17.43 -> 20.96 s at 2593 tokens within one afternoon when the request generated 48 tokens instead of 8; unexplained.
- The plans first credited the in-binary PASSIVE setting for 38.55 -> 29.93 s at 2582 tokens; the 09-21 notes show it never applied and the gain came from setting the variable in the shell.
