# open_kernels working notes (verbatim from project memory)


As of 2026-09-02, both project-gating unknowns for replacing FLM's closed
xclbins with our own IRON/mlir-aie kernels are retired (plan +
published verdict: docs/open-kernels-feasibility.md):

- **0a toolchain**: mlir-aie 1.4.2 + Peano build xclbins in WSL
  (`~/ironenv142`, `~/mlir-aie` at tag v1.4.2). `xclbinutil` + `aiebu-asm`
  are NOT in the wheel and WSL has no sudo — built from XRT master in a
  Docker `ubuntu:24.04` container into `~/xrt-tools/{bin,lib}`
  (recipe: scratchpad build_xclbinutil.sh). Build a design with
  `tools/open-kernels/build_design.py` (@iron.jit) or `build_mlir.sh` (raw
  MLIR). Our own kernels run through phlegm's driver: ROT13 byte-exact.
- **0b expert fetch**: a shim DMA descriptor into a big DDR pool, retargeted
  to a runtime-chosen slab and enqueued by CONTROL PACKETS with no host
  round-trip. Array->shim-control directly does not deliver (AIE2 target
  model); bounce the packet words through DDR (S2MM out, shim MM2S back into
  its own TileControl) — a legal flow, and how FLM does it (its shim BDs
  4-7/12-15 are written-but-never-enqueued by the txn stream; 32 = 8 experts
  x 4 stripes). Proof: designs/expert_fetch/ddr_bounce_fetch.mlir, idx 3/7
  give exact per-slab sums.

**Phase 1 progress (2026-09-02):** q4_1 GEMV (`designs/gemv_q4`, pool-order
band law half=c%2 kt=c/2) and q8 lm_head (`designs/lm_head_q8`, supertile
order quarter=c%4 kt=c/4) both EXACT vs fp64 references from the captured
pool bytes (cos 1.0, maxrel ~1e-5). lm_head full 21.4 ms vs FLM 15.4 ms.
Harness per design: `make_test.py` (slice pool -> w/x/ref + run cfg, WSL
python) -> `open-qwen-npu npu run_<tag>.cfg` (Windows) -> `compare.py`.
Lessons: vegah's kernels port unchanged (same chunk layout); runtime int args
from `range_` work (one entry point per kernel); hand-built
`TensorAccessPattern` for uneven core slices. DeltaNet step
(`designs/deltanet`) also EXACT (S_out/o maxrel 6e-6, 0.44 ms/layer): S
streamed twice in 16-row slices, bf16 hi/lo splits for every fp32 product.
HARDWARE TRAPS (silent hang, ERT state 8): shim DMA start queue = 4 BDs per
channel (await fills with `fill(wait=True, group)`+`finish()` before queuing
more); column shim = 16 BDs total (pin one worker per column with
`Worker(tile=Tile(c,2))` when a core needs many fills); dma_bd verifier rejects
zero strides (no repeat-dim trick). Glue kernel (`designs/dn_glue`: conv1d +
SiLU + L2 norm + decay/beta records) also fp32-exact, 0.71 ms. IRON TRAPS
from it: `release(n)` frees the OLDEST n elements (copy held elements to a
Buffer); Python-unrolled loops overflow 16 KB program memory
(`XAIE_INVALID_ELF`) -> use `range_`; objectfifo allocates depth+1 buffers;
hardware tanh/inv/invsqrt are ~1e-2 LUTs -> `vexp32`/Newton helpers in
dn_glue.h; small worker stack (0xD00) hangs with fp32 vector code (0x1800
ok); jit design cache + aiecc final.prj reuse stale kernel objects ->
build_design.py wipes final.prj each build (identical results across
"rebuilds" = stale cache).

**DIAGNOSED 2026-09-02: the divergence is FLM, not the CPU model.** On the
3LiF ([L,L,F], full_attention_interval=3) capture, FLM contributes NOTHING
from the full-attention block: zeroing layer-2 attention in the replica
reproduces FLM's captured decode logits at 0.998 (same argmax) and its
prefill final hidden at 0.995; all inputs to that block (q/gate/k/v, FLM's
own KV cache) match ours at 0.9994+. Matches "FLM mis-executes interval-3"
([[pruned-qwen36-flm-project]]). So for interval-3 models the HF-faithful
CPU replica is the oracle and the open kernels (corr 1.00000 vs it) are the
correct engine; FLM's fused kernels cannot run Josh's pruned model right.
