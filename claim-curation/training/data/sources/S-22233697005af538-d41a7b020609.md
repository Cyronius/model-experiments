# Linux amdxdna without XRT: raw ioctl dispatch, sync rules, GPU buffer imports, errors and a QoS wedge (upstream hipfire report)

Sources (C:/code/hipfire): `docs/plans/2026-09-16-halo-npu-max.md:22-48` (status blocks), `:226-242` (raw dispatch proof), `:305-309` (import results), `crates/hipfire-xdna/src/lib.rs:6-47` (measured ABI notes), `crates/railgun/src/npu/mod.rs:11-160,413` (runtime), `docs/npu/report.md:11-22` (host inventory), `:43-58` (M1 hello), `:734-761` (dma-buf amendment), `:847-893` (QoS incident, low-RAM corruption), `docs/npu/coop-down27.md:56-61` (mapping matrix), `docs/npu/gemm_i8.md:240-247`, commit `a053503c8`.

## Raw dispatch without XRT

- A libc-only path ran mlir-aie PDIs and instruction streams bit-exact against XRT, also after context destroy/recreate: 64 MiB DEV_HEAP BO at a 64 MiB-aligned host VA, CREATE_HWCTX (all-zero QoS, max_opc 2048, num_tiles 32), DEV BO for the PDI, CONFIG_HWCTX CU (16 B payload), DEV BO for the instructions, SHMEM BOs for data, one CMD BO, EXEC_CMD, then `DRM_IOCTL_SYNCOBJ_TIMELINE_WAIT` (WAIT_FOR_SUBMIT) on the hwctx syncobj at the EXEC_CMD seq, then a check for ERT state 4.
- The working ERT_START_CU packet: header `0x30010001`, cu_mask 1, payload opcode 3, instruction address, instruction size in bytes (not words), then bo0..bo4. bo0 sits at payload offset 0x14, so the u64 slots are 4-mod-8 unaligned.
- Kernel 7.0 has no WAIT_CMD ioctl. The syncobj timeline wait works instead.
- `SYNC_BO FROM_DEVICE` returns EINVAL for SHMEM BOs on this driver; `TO` works. Readback uses CPU `clflush` per 64 B line with `mfence` before and after. The source says this matches the installed XRT shim's default non-coherent sync (`clflush_data`).
- The output buffer must also be flushed before the run, so a later dirty-line eviction cannot overwrite device output.
- The readback flush averaged 1.475 ms for a 35.65 MB GEMM output and 17.345 µs for a 524,288 B output (all iterations).
- Only bo0..bo4 reach the firmware, so every design uses at most 5 DDR-patched buffers. Consistent with F-0012.

## GPU buffer imports (gfx1151 iGPU)

- `SYNC_BO` on an imported dma-buf handle oopses the kernel (7.0.0-31). Imported buffers use CPU flush only. The command BO must be of CMD type.
- XDNA→XDNA PRIME import ran correctly, but mmap of the imported BO returned EINVAL, and importer-side sync or a direct dma-buf mmap killed the probe session.
- NPU→GPU import fails: KFD rejects dma-bufs that amdgpu did not export (`amdgpu_amdkfd_get_dmabuf_info`).
- GPU `hipMalloc` buffers imported into amdxdna were read and written bit-exactly by an NPU kernel (control 6/6, read 12/12, write 36/36). Import setup took 0.8-3.9 ms, once.
- A HIP VMM host allocation exported with `hipMemGetHandleForAddressRange` aliases only bytes written before the export. After the amdxdna import, GPU writes do not show through the dma-buf and dma-buf writes do not reach the GPU (64 KiB to 16 MiB, pinned or uncached). This withdrew the source's 2026-10-02 "zero-copy" verdict.
- Live sharing works with anonymous host pages pinned by amdxdna as a userptr BO and `hipHostRegister`ed for the GPU. A three-way alias check (CPU, GPU kernel, NPU map) passes on it.
- All 16 page and flag mixes (4k, THP, hugetlb 2M, 1G × hipHostRegister 0 / Portable / Mapped / CoarseGrained) were accepted by amdxdna. The GPU read 238-241 GB/s and wrote 220-227 GB/s on the shared pages.
- Linux 7.2 amdxdna refuses mmap of a userptr BO with EINVAL. The caller's own map of the same pinned pages works as the CPU view (commit a053503c8).

## Errors, hangs and recovery

- Closing the PDI BO before the hardware context logged `aie2_hwctx_restart: Config cu failed, ret -22` at teardown.
- Hung array designs gave syncobj ETIME after 3 s or 30 s waits with an empty kernel log. The next fresh context ran normally, with no reboot.
- Shim BD AxQoS 15 wedged the NPU: the first submit timed out, a firmware status query timed out, then device open failed `GET_INFO` with errno 22, and the kernel logged `aie2_smu_exec: smu cmd 4 failed, 0xff`, `aie2_smu_init: Access power failed, ret -22` and a resume failure -22. Recovery took a reboot. The emitter now keeps vendor BD word 5 (AxCACHE 2, AxQoS 0).
- A write source in low memtile memory on a reused context gave exactly 1024 bad words at a 16384-byte stride, value `0x00cd0cd0` (expected `0xb0000000`). That constant appears once, at offset `0x4d430` of the decompressed `npu_7.sbin.zst` (429680 B). A source at memtile 0x14000/0x18000 fixed it.

## Doubtful

- The firmware as the writer of `0x00cd0cd0` is the source's inference; the writer is not proven.
- The 2026-09-16 `hipMalloc` import result may hide the same write-before-export limit as the VMM case; the source does not say when the GPU wrote. The source's own reading of amdgpu says VRAM buffers migrate to GTT (a copy) for this importer.
- Bears on Q-0016: on Linux the sync for device-to-host reads is a CPU clflush loop with mfence on both sides; hipfire saw no stale reads with it, but ran no 1-in-3000 style stress.
- Bears on Q-0019: on Linux/HIP, a GPU-exported VMM buffer did not stay live after the NPU import, while a userptr BO plus `hipHostRegister` did. The Windows/Vulkan case stays untested.
