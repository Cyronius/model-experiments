# Strix Halo on Linux: per-submit cost, transaction-stream size, retained and chained commands, and a CPU-free GPU→NPU ring (upstream hipfire report)

Sources (C:/code/hipfire): `docs/npu/report.md:491-508` (fixed cost fit), `:573-591` (expert sizes), `:596-629` (railgun table, ring latency), `:639-660` (grouped experts), `:712-732` (GPU-driven ring), `docs/npu/railgun-npu.md:10-20,38-56,57-96,134-144`, `docs/npu/CHANGELOG.md:5,18`, `docs/npu/ief15-n0.md:140-141`, `docs/npu/coop-down27.md:70-73`, `docs/plans/2026-09-16-halo-npu-max.md:234-240`, commit `b92f636bc`.

## Per-submit cost

- A no-op command (transaction stream with one WRITE32) costs 59 µs p50 for one EXEC_CMD round trip. Queued retained commands (×8, ×32) or ERT_CMD_CHAIN ×8/×32 cost 20-25 µs per command; a chain of 8 no-ops took 203 µs.
- A V9 512²×64 GEMM (≈1 µs of compute) took 214 µs alone and 167 µs chained. The source puts ≈150 µs of that on the firmware's execution of the 51 KB transaction stream (1746 ops) that re-initialises the whole array every submit.
- A lean stream (11-14 KB) repairs only what a completed run changed and cuts that to ≈50 µs: V9 gate_up 4096×1280×2560 1051 → 889 µs per GEMM, down 4096×2560×640 562 → 408 µs. It is valid only right after a completed submit of the same PDI on the same hwctx, with no other hwctx in between (consistent with F-0013).
- Over no-compute runs at two M and four K values, the full-stream designs showed a fixed ≈215 µs per submit, independent of M and kc.
- At expert sizes (M 64-512) every variant sat at 280-360 µs per submit, so this intercept is ≥ 75% of the time.
- Same stock artifacts on 2026-09-16: a tiny 512×64×256 GEMM took 102.737 µs median via raw ioctls and 166.4 µs via XRT (separate batch); a 16 ms GEMM took 16345.271 against 16300.5 µs. The source claims no causal speedup.
- The NPU needs ~45-50 µs to start each command, measured on an empty ring and independent of stream and BO size. Submit to first done took 50-55 µs; the first command on a fresh context took 1.6 ms.
- The driver sets the command state back to NEW at job start, so a retained command BO needs no header rewrite; only changed argument address words get patched. Eight retained GEMMs took 1408 µs against 1865 µs eager.
- One START_CU can run E experts back to back (expert 0 full stream, the rest lean). E=64 makes a 935 KB stream and ran fine. Per expert: gate_up 1280×2560 201-234 µs, down 2560×640 113-131 µs, against eager 396-597 and 309-516 µs in the same process.
- Alternating two designs (two PDIs) on one hardware context added +1020.6 µs per submit on IEF15 down (14333.2 vs 13312.6 µs) and +1198.0 µs on gate_up (11201.9 vs 10003.9 µs).
- Two contexts on disjoint 16-tile partitions stayed untested: the probe used a one-shot single-core design, whose resubmission timed out at 3 s (no wedge).

## CPU-free work ring

- The ring is one START_CU whose stream loops over slots. A self-looping shim BD copies the slot's `seq` word from DDR into memtile memory, and the stream MASKPOLLs that word; after the C SYNCs one 64 B DMA write posts the done line.
- With the CPU as producer: publish → done seen p50 4.5 µs (min 1.4-2.6, p99 51-73 µs on each round's first slot); done → done 5.3 µs when slots were published ahead. Paced and published-ahead runs gave the same 897 µs per GEMM slot.
- Ring plus lean streams: gate_up 29.93 busy / 29.90 wall TOPS (897 µs per slot), down 31.87 / 31.80 (421 µs).
- With the gfx1151 iGPU as producer (shared userptr pages): GPU publish → NPU done → GPU observe p50 3.13 µs (min 2.73); one uncached poll load costs 0.24 µs.
- Full GPU → NPU → GPU round trip with a 512×1280×2560 int8 GEMM per run: 271 → 128 µs per run (`--slots 8 --nslots 4 --rounds 16`: 8 runs per command over 4 ring slots; median of 3 processes; byte-exact), on the Linux 7.2 "halo" box. 512×2560×640: 164 → 113 µs. Steps: two GPU streams, lean re-arm, rounds queued one ahead, B kept resident in the memtile.

## Doubtful

- The commit title says 164 → 112 µs for the down shape; CHANGELOG.md says 113 µs.
- F-0022 found re-executed XRT runlists slower than fresh runs on FLM kernels (Windows); here retained and chained raw commands were faster than eager ones. Different stack and mechanism.
- F-0064 gives ~4 ms for a first dispatch on Strix Point/Windows; here 1.6 ms (first ring command) and ~2.5 ms (tiny GEMM after context recreate, 2026-09-16).
- Bears on Q-0005: on Linux the no-op round trip is 59 µs (20-25 µs queued), but firmware execution of the transaction stream adds roughly 150 µs per 51 KB. Stream size may explain part of the spread in per-call floors.
- Bears on Q-0006: a design switch inside one context costs ~1.0-1.2 ms per alternating submit at these sizes.
- Bears on Q-0013: on Linux/Halo one context ran 20626 submits in one loop and a 935 KB 64-expert stream with no timeout.
