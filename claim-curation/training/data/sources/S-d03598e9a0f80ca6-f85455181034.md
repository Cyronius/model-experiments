# Linux/XRT facts reported by a fork (Nulifyer/llama-xdna-hybrid), and related public NPU reports

Sources (C:/code/npu-prefill-engine): `.claude/plans/open-issues-2026-10.md:44-60` (WSL check), `:62-103` (fork summary), `:105-172` (Linux design incl. locked memory and packages); `.claude/plans/npu-ceiling-reports.md:89-129` (public issue drafts). The fork's results are the plan author's summary of someone else's commits, not reproduced here. Treat as leads to verify.

## Measured by ggml-xdna (WSL, 2026-10-12)

- WSL's Ubuntu 24.04 has no `/dev/accel`, the node the Linux NPU driver creates. WSL passes the GPU through (`/dev/dxg`) but not the NPU, so nothing NPU-side can be run or timed from WSL; only builds and host-only tests.

## Reported by the fork (hearsay)

- Fork: Nulifyer/llama-xdna-hybrid, a fork of ggml-xdna at v0.1.0 (f5fe5b4), 10 commits from 2026-10-06.
- Hardware runs on a Ryzen AI 9 HX 370 under Ubuntu 24.04 with XRT 2.25 and Ubuntu 26.04 with XRT 2.21: the NPU tests passed (start-up test multiply, claiming, matmul accuracy, the NaN catch, the memory limit), and an 8,192-token prompt took 7-20% less time than the GPU alone (Qwen3.5-2B, two sittings).
- Built against ggml-xdna's vendored XRT 2.20 headers, it ran with XRT 2.25 (headers older than runtime worked).
- The NPU code needed almost no change from Windows on the same chip; the change was mostly platform bits (finding the add-on folder with `dladdr`, memory info from `/proc/meminfo` and a container memory limit).

## Planned/documented, not yet confirmed on hardware (ggml-xdna's own design notes)

- XRT locks its buffers in memory and Linux caps how much a process may lock. The fork had to lift the cap to unlimited; Docker's default (a common desktop default too) is 8 MB. The planned behaviour (raise the soft limit as far as allowed, shrink the weight-copy limit or refuse the NPU) is "exact behaviour to confirm on hardware".
- Driver/package pointers given: kernel with the `amdxdna` driver (recent mainline kernels, or `amdxdna-dkms`); XRT as `libxrt-npu2` in Ubuntu 26.04's own archive, the lemonade PPA on Ubuntu 24.04 and 25.10, `xrt` plus `xrt-plugin-amdxdna` on Arch; building needs `uuid-dev`, which XRT's headers include on Linux; the add-on would load `libxrt_coreutil.so.2` at run time and a small wrapper library compiled against vendored headers.
- Device node checked for: `/dev/accel/accel0`.
- Open question to settle on Linux: is the roughly 26 GiB NPU buffer ceiling (see the 2026-10-04 note) Windows' or the NPU's? The ceiling-recheck program is `tools/npu-ceiling-repro` ported to Linux (not done).

## Related public reports quoted in ggml-xdna's draft issue comments (2026-10-04; all secondhand)

- FastFlowLM #647 (embeddings change with history): draft comment suggests an NPU-side buffer going bad past about 26 GiB; cites FastFlowLM #720 as saying FLM uses about 27 GB while running.
- FastFlowLM #611 (Qwen3.6 MoE turns to gibberish): reporter's Task Manager showed about 24-26 GB. The draft notes the Linux report in that thread "may have a different cause; we've only seen this on Windows".
- amd/RyzenAI-SW #402: an earlier session's buffer turns all-NaN, no error, after a second session runs; recreating the buffer heals it (the draft says the signature matches but uses far less memory). ggml-xdna filed its own repro as amd/RyzenAI-SW #404 (2026-10-04).
- Suggested check from the draft: add the Performance Monitor counter `GPU Adapter Memory\Shared Usage` for each adapter; if the NPU's counter stops rising near 26 GiB while a program is still loading, it is likely the same fault.
- Status of the three comments: drafts 2-4 were not posted at the time of writing.

## Doubtful

- The 7-20% speedup claim and the XRT versions are the fork author's, relayed through a plan summary. The plan author explicitly marks Linux support "built and tested without an NPU, not tested on hardware".
- "Qwen3.5-2B" appears in the fork summary; no other doc in this repo mentions that model, so the name could be a transcription slip (Qwen3-1.7B / Qwen3.8 are what the repo uses).
